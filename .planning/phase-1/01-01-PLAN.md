## Overview

This plan delivers a single file (`app/plugins/competence.py`) in 8 waves. Each wave adds an independent layer, verified before the next wave begins. All waves modify the same file, so they execute sequentially within this single plan.

**Key decisions from research (locked in):**
- Plugin extends `ToolkitPlugin` with `id="competence"`, `name="Competence Matrix"`, `icon="📈"`, `order=45`
- Module-level `plugin = CompetencePlugin()` for auto-discovery by `_discover_plugins()`
- Jira auth via `config.load_jira_config()` returning `{"email": "...", "token": "..."}`
- HTTP client: `httpx.AsyncClient` + `httpx.BasicAuth` (NOT sync `requests`)
- SQLite in WAL mode, co-located at `app/plugins/competence_cache.db`
- Background sync via `asyncio.create_task()` with `in_progress` flag (NOT FastAPI BackgroundTasks)
- Route registration: `@app.get/post` decorators inside `register_routes(app)`, paths `/api/competence/*`
- State machine with configurable `RETURN_FROM` / `RETURN_TO` status sets
- Stats grouping: `pd.Grouper(key='transition_date', freq='2Q')` with formatted labels `"YYYY QX-QY"`
- DB schema from FR2: `sync_state(key TEXT PK, value TEXT)` key-value + `transitions(id INTEGER PK AUTO, ticket_key, transition_date, action_type CHECK('ATTEMPT','RETURN'))`

### Wave 4: State Machine + Changelog Parser

Implements the ATTEMPT/RETURN detection algorithm from changelog data.

<tasks>

<task type="auto">
  <name>Task 4.1: Implement changelog parser with configurable state machine</name>
  <files>app/plugins/competence.py</files>
  <action>
Implement `_parse_changelog(changelog: dict, ticket_key: str) -> list[dict]` following RESEARCH.md Pattern 5.

**Configurable status sets** (module-level constants, before the class):
```python
RETURN_FROM = {"For Testing", "In Testing", "Test Failed", "Testing Failed"}
RETURN_TO = {"In Development", "In Progress", "Gathering Information", "To Do", "New"}
ATTEMPT_TO = {"Developed", "For Testing", "In Testing"}
ATTEMPT_FROM = {"In Development", "New", "Gathering Information"}
```

**Algorithm** (per FR4):
1. Iterate `changelog["values"]` chronologically (Jira returns them in order)
2. For each entry, iterate `entry["items"]` — keep only items where `item["field"] == "status"`
3. **Rule 1 (ATTEMPT):** When `fromString` is in `ATTEMPT_FROM` AND `toString` is in `ATTEMPT_TO`, AND the `author.accountId` matches current user → record `{"ticket_key": ticket_key, "transition_date": entry["created"], "action_type": "ATTEMPT"}`. 
   - To get current user: make one call to `/rest/api/3/myself` at sync start and cache `current_account_id`.
4. **Rule 2 (RETURN):** After an ATTEMPT has been recorded for this ticket (tracked in a local set), if status changes FROM a `RETURN_FROM` status TO a `RETURN_TO` status (any author) → record RETURN transition.
5. **Deduplication (FR4.4):** Before yielding a transition, check SQLite: `SELECT 1 FROM transitions WHERE ticket_key=? AND transition_date=? AND action_type=?`. Skip if exists.
6. Return list of dicts: `[{"ticket_key": str, "transition_date": str (ISO), "action_type": "ATTEMPT"|"RETURN"}, ...]`

**State tracking per ticket:** Within `_parse_changelog`, maintain `has_attempt = False` flag per ticket. Set to True on first ATTEMPT. Only detect RETURNs after `has_attempt` is True. This prevents counting pre-development status changes as returns.

**Edge cases:**
- Empty changelog (`"values": []`) → return empty list
- No status items in changelog → return empty list
- Missing `fromString`/`toString` → skip that item (don't crash)
- Multiple ATTEMPT/RETURN cycles on same ticket → each cycle produces one ATTEMPT + one RETURN (track has_attempt reset after RETURN, or track "in_testing" state)
  - Better approach: track `in_testing` boolean. ATTEMPT sets it True. RETURN sets it False and records a return. Another subsequent ATTEMPT sets it True again.
  </action>

**Flow:**

   - If `last_sync` is None (first sync) → build JQL: `assignee WAS currentUser() OR reporter = currentUser()`

5. **Search for issues (FR3.3):**
   - Call `await _api_get("search", jql=jql, fields="key", maxResults=1000)`

   - Handle pagination: if `total > maxResults`, loop with `startAt` parameter

   - Use `asyncio.Semaphore(5)` to limit concurrent requests
   - For each issue key: `await _api_get(f"issue/{key}/changelog", maxResults=100)`
   - Handle pagination for changelogs with >100 entries (loop with `startAt`)

7. **Parse each changelog (FR4):**
   - Call `_parse_changelog(changelog_data, issue_key)` for each issue
   - Collect all transitions into a flat list

8. **Insert transitions into SQLite (FR2, FR4.4):**
   - For each transition, check deduplication: `SELECT 1 FROM transitions WHERE ticket_key=? AND transition_date=? AND action_type=?`
   - Insert new transitions: `INSERT INTO transitions (ticket_key, transition_date, action_type) VALUES (?, ?, ?)`
   - Use `_db_lock` around all write operations
   - Batch inserts: use `executemany()` for efficiency

9. **Update last_sync (FR4.5):**
   - `await _db_set("last_sync", datetime.utcnow().isoformat())`

10. **Clear in_progress:** `await _db_set("in_progress", "0")`

11. **Log summary:** `print(f"[competence] Sync complete: {len(issues)} issues, {len(transitions)} transitions")`

**Error handling (FR3.6):**
- Per-issue failures: `try/except` around each changelog fetch; log `[competence] Failed to fetch changelog for {key}: {error}`; continue to next issue
- The `_db_set`/`_db_get` helpers should be robust: write to `sync_state` using `INSERT OR REPLACE INTO sync_state (key, value) VALUES (?, ?)`

**`_db_get(key: str) -> str | None` helper:**
```python
def _db_get(key: str) -> str | None:
    with _db_lock:
        conn = _get_db()
        row = conn.execute("SELECT value FROM sync_state WHERE key = ?", (key,)).fetchone()
        conn.close()
    return row["value"] if row else None
```

**`_db_set(key: str, value: str)` helper:**
```python
def _db_set(key: str, value: str):
    with _db_lock:
        conn = _get_db()
        conn.execute("INSERT OR REPLACE INTO sync_state (key, value) VALUES (?, ?)", (key, value))
        conn.commit()
        conn.close()
```

**Async wrapper for DB operations:** Since stdlib `sqlite3` is synchronous, wrap in `asyncio.to_thread()`:
```python
async def _db_get_async(key: str) -> str | None:
    return await asyncio.to_thread(_db_get, key)

async def _db_set_async(key: str, value: str):
    await asyncio.to_thread(_db_set, key, value)
```
Use `_db_get_async`/`_db_set_async` inside async functions. The sync versions `_db_get`/`_db_set` are for use in synchronous code paths (e.g., `startup()`).

   result = []

   def _format_2q_label(period: pd.Period) -> str:

       year = period.year
       # 2Q periods: Q1 = Jan-Jun (Jan-Mar + Apr-Jun), Q2 = Jul-Dec (Jul-Sep + Oct-Dec)
       if period.quarter == 1:
           return f"{year} Q1-Q2"
       else:
           return f"{year} Q3-Q4"
   ```

   - `2Q` freq: Q1 = first half-year (Q1+Q2), Q3 = second half-year (Q3+Q4)
   - So `period.quarter == 1` means first half, `period.quarter == 3` means second half.

```

Total: ~350-400 lines.

### Import Order Convention (NFR5)
Follow `release_creator.py` exactly:
1. `from __future__ import annotations`
2. stdlib (`import os, json, asyncio, sqlite3, threading, datetime`)
3. third-party (`import httpx, pandas as pd`, `from fastapi import FastAPI, HTTPException`, `from pydantic import BaseModel`)
4. local (`from app.plugins.base import ToolkitPlugin`, `from app import config`)

### Error Handling Pattern (NFR5)
- Route handlers: `try/except Exception as e: raise HTTPException(500, str(e))`
- Background sync: `try/except` per-issue; log + continue
- Non-fatal: `print(f"[warn] ...")` and continue

### SQLite Concurrency
- All writes go through `_db_lock`
- Reads in WAL mode don't need lock
- Use `asyncio.to_thread()` for DB calls inside async functions
- Connection created per-operation (with `check_same_thread=False`), closed immediately after

### Jira API Rate Limiting
- `asyncio.Semaphore(5)` limits concurrent changelog requests
- `httpx.Timeout(30.0)` prevents hanging requests
- Consider adding `asyncio.sleep(0.1)` between requests if rate-limited (not implementing in Phase 1 unless needed)

### Missing Jira Config Handling (NFR4)
- `_get_client()` raises `HTTPException(503)` if no credentials — caught by route handler
- `startup()` catches all exceptions, logs warning, does not crash
- Stats endpoint works with empty SQLite (no Jira dependency)
